# SQL / ETL 研发评审

## 1. 评审定位

本技能不是通用 SQL 美化器，也不负责凭经验补齐表名、字段名、主键、指标口径或血缘关系。

评审默认面向本项目的 **T+1 离线数仓**，主要运行在 Hive / Spark，存储通常为 ORC，按业务约定进行日级或其他周期的分区跑批。实时链路（Kafka / Flink / Doris 等）必须先确认架构，再启用实时专项检查。

团队规范的主要事实来源：

- `raw/99-archive/01-公司开发规范/招商城科_数据项目开发指引v1.0.pdf`：数据架构、分层、命名、字段、分区、Hive SQL 优化与开发要求，重点页码 2、8-15、20-32、39-57。
- `wiki/sources/公司开发规范.md`：团队规范资料目录与当前知识库摘要。
- `wiki/concepts/数仓分层.md`：当前 Wiki 对数仓分层的摘要；如与原始规范不一致，以已查证的原始规范或主人明确口径为准。
- `AGENTS.md`：本知识库事实证据、留白和来源坐标规则。

原始规范文件为 2020 年版本。若当前平台、调度框架或最新团队制度已有变化，必须标注“待确认”，不能把旧文档直接当成现网事实。

## 2. 事实证据与禁止猜测

### 2.1 证据等级

评审中涉及表、字段、依赖、Join 关系、分区、指标口径时，按以下证据等级处理：

- **L1 权威证据**：目标 SQL 的 `FROM` / `JOIN` 原文、表 DDL 字段注释、现网调度脚本、数据字典、需求文档、主人明确口述。
- **L2 可追溯推断**：由 L1 的 Join 条件、别名映射、字段注释、CTE 引用链推导出的关系。
- **L3 无依据猜测**：按表名或行业习惯补全字段、主键、唯一性、上下游、业务含义或“通常应该有”的节点。

执行要求：

1. 每个表名、字段名、Join 边、指标定义和数据血缘都必须能定位到 L1；否则不写成事实。
2. 证据不足时写入“待确认问题”，不得用看似合理的内容填空。
3. 报告中为实体标注证据坐标，例如：`表名（文件.sql:117，JOIN）`。
4. 不把别名当作源字段。`user_id AS one_user_id` 只能证明输出别名，不能证明源表存在 `one_user_id`。
5. 名称相近的表不能互相套用字段和粒度；每张表单独查证。
6. 主人明确纠正的口径视为 L1，并覆盖之前未经证实的推断。
7. 无法证明的问题降级为 P1 或 P2，并给出可执行的验证 SQL；不得为了“有结论”而报 P0。

### 2.2 恶意或危险代码

如果输入文件出现明显恶意行为、凭据窃取、破坏性命令、绕过权限、隐蔽外传数据等内容，不得改进、扩充或优化该代码。可以做高层行为分析和风险报告，但必须停止代码增强。

## 3. 团队数仓规范基线

### 3.1 数仓分层与引用关系

团队开发规范定义的主要数据区为：

- `STG`：临时数据区，缓存源系统加载数据；源表原则上保持一致，不做整合。
- `ODS`：操作镜像区，保存源系统当前全量数据；状态数据做历史拉链，流水数据做追加。
- `NDS`：贴源非规范数据区，用于个性化、手工或暂不适合整合到基础模型的数据；不能无期限作为长期公共数据区使用。
- `DWD`：基础数据区，细分为 `PDM` 基础模型区和 `SUM` 通用汇总区。
- `DWS`：业务领域主题区，按业务主题提供数据服务。
- `ADS`：应用数据区，面向具体应用和看板。

按原始规范的直接引用关系评审：

- `STG` 可提供给 `ODS`、`NDS`、`PDM`。
- `ODS` 主要提供给 `PDM`；也可供 `ADS` 使用，但必须重点管控和评审。
- `NDS` 可提供给 `SUM`、`DWS`、`ADS`，使用时需要管控和评审。
- `PDM` 可结合 `STG`、`ODS`，加工结果可提供给 `SUM`、`DWD`。
- `SUM` 主要来源于 `PDM`、`NDS`，汇总结果提供给 `DWS`。
- `DWS` 可使用 `PDM`、`SUM`、`NDS`，加工结果主要提供给 `ADS`。
- `ADS` 可获取 `ODS`、`NDS`、`DWS`，但直接使用 `ODS` / `NDS` 时必须严格管控。
- `ADS` 之间不允许相互关系连接；应访问业务领域主题区、通用汇总区或基础模型区。

发现跨层引用不符合上述关系时，先检查是否有项目级审批或最新规范依据；没有依据时至少报 P1 待确认，不得直接判定为合理。

### 3.2 表形态与加工策略

团队规范定义的表形态包括：

- `CS`：当前状态表，只保留当前全量数据，不保证准确历史。
- `SS`：状态快照表，含快照日期，快照日期是主键组成部分；应按保存策略清理过期快照。
- `HC`：状态历史拉链表，以开始日期、结束日期描述记录变化。
- `TF`：流水表，保存事件流水、流水号和交易日期或会计日期，通常追加。
- `SR`：统计结果表，含统计日期，通常按统计日期管理历史。
- `DIM`：维度表，原则上每天全量下发。
- `MID`：中间表，保存加工过程中的中间结果。
- `BAK`：备份表，用于表操作前后的数据备份。

评审必须核对：表名后缀、目标表实际语义、写入方式和历史保存方式是否一致。例如，`SS` / `SR` 不能无理由追加造成重复快照，`TF` 不能按快照覆盖丢失流水，`HC` 必须检查开始结束日期和变更逻辑。不能只根据后缀臆断真实粒度，必须结合 DDL 和 SQL 证据。

### 3.3 库表命名

按原始规范核查库表命名，不凭经验改名：

- `STG_<二级组织简称>`、`NDS_<二级组织简称>`、`ODS_<二级组织简称>`。
- `DWD_<二级组织简称>_P`：PDM；`DWD_<二级组织简称>_S`：SUM。
- `DWS_<二级组织简称>_<业务领域>`。
- `ADS_<二级组织简称>_<APP>`。
- ODS 表形态示例：`ODS_CMSK.HOCMSK0101_EMPLOYEE_INFO_CS`。
- DWD 表形态示例：`DWD_CMSK_P.HDP01_EMPLOYEE_INFO_CS`、`DWD_CMSK_S.HDS01_EMPLOYEE_INFO_CS`。
- DWS 表形态示例：`DWS_CMSK_FIN.HS01_FIN_EMPLOYEE_INFO_CS`。
- ADS 表形态示例：`ADS_CMSK_BDRP.HA01_EMPLOYEE_INFO_CS`。

命名问题通常为 P2；若导致跨层误用、任务找错表或覆盖错误目标，可升级为 P1/P0，必须写明证据和影响。

### 3.4 字段与保留字段

按规范检查：

- `STG`、`ODS` 字段名原则上与源数据保持一致。
- 业务字段使用字母、数字和下划线，多个单词用下划线分隔，名称简洁明确。
- 字段必须有描述信息；禁止使用数据库关键字作为字段名。原规范以 `time`、`date` 为例。
- 表之间表示同一含义的字段应保持相同数据类型；Join 前如类型不一致，必须显式转换并说明风险。
- 字段类型应满足精度和查询效率要求；不要无依据扩大或缩小类型。
- 规范列出的保留字段包括 `LOAD_DATE`、`ETL_DATE`、`START_DATE`、`END_DATE`、`DEL_FLAG`、`Created_time`、`Created_user`、`Updated_time`、`Updated_user`。实际任务若采用现网变体，必须以 DDL 或现网模板核对。
- Hive 与 MPP 类型映射及 MPP 类型/长度注释要求，只有在目标平台确实涉及时才检查；不能把 MPP 约束套到纯 Spark 临时结果表上。

## 4. 输入要求与评审前提

优先收集：

- SQL 或任务脚本全文、目标表 DDL；
- 任务所属层级、库名、表形态和分区定义；
- 每张输入表的 DDL、字段注释、主键或业务唯一键、数据粒度；
- 需求文档、指标口径、统计周期和时间字段定义；
- 调度周期、补数范围、重跑方式、写入模式；
- 近期开数、行数、分区大小、倾斜 key、执行计划或任务日志。

缺少 DDL、唯一键、真实粒度或数据分布时，可以做静态评审，但必须写明：

> 当前结论未结合真实表粒度、唯一性和数据分布，需补充元数据或样本后复核。

在此情况下，结论不得为“通过”，只能是“有条件通过（待补元数据）”或“不通过”。

## 5. 强制规则：三行粒度

在输出“通过”之前，必须明确回答：

```text
每张输入表的一行代表什么？
每次 Join 后的一行代表什么？
最终目标表的一行代表什么？
```

至少按以下维度写清楚：业务实体、业务事件、统计周期、分区粒度、是否允许重复。

若无法回答，直接阻断“通过”结论。若某个 Join 的一对一/一对多关系无法由 DDL、唯一键或数据验证证明，按 P1 待确认处理；若已经能从 SQL 证明会产生多对多膨胀，按 P0 处理。

## 6. 评审流程

1. **识别任务边界**：平台（Hive / Spark）、所属数据层、目标表形态、分区与写入方式。
2. **建立证据表**：逐个登记目标表、输入表、CTE、`FROM` / `JOIN`、过滤条件、聚合和写入语句的文件行号。
3. **复原数据流**：只根据 SQL 原文画出 CTE、子查询、Join、Union 和聚合链路。
4. **执行三行粒度检查**：先判断每张输入表、Join 后和目标表粒度。
5. **按团队规范逐项检查**：分层引用、表形态、命名、字段、分区、Join、过滤、去重、指标、性能、幂等、补数、测试和交付。
6. **生成验证 SQL**：对唯一性、重复、行数、空值、分区、指标对账和数据倾斜给出可执行验证。
7. **分级与结论**：按 P0/P1/P2 输出，并严格遵守“无 P0、无 P1、三行粒度明确”才可通过。

## 7. 逐项检查清单

### 7.1 业务口径与指标

- 指标定义、统计对象、分子分母、去重键、统计周期是否来自需求或现网口径。
- 业务时间与入库时间是否区分；同环比、快照日期、分区日期是否混用。
- 指标在不同层级是否发生 `COUNT(DISTINCT)`、`SUM` 或先聚合后 Join 的口径变化。
- 过滤是否遗漏无效、删除、撤销、过期、退款或其他已在需求中明确排除的记录。
- `NULL`、空字符串、默认值是否会改变业务含义。

### 7.2 粒度、Join 与笛卡尔积

- 每个 Join 是否写出完整 `ON` 条件；禁止用 `WHERE` 代替 Join 条件造成笛卡尔积风险。
- 是否存在无 Join 条件、不等值 Join、`OR` Join 或多表连接条件不完整。
- Join 两侧键是否唯一，Join 前是否需要按业务键去重或取最新记录。
- 关联字段类型是否一致；不一致时是否有显式 `CAST` 和验证。
- 一对多是否会放大事实记录；放大后的指标是否仍符合口径。
- `LEFT JOIN` 后在 `WHERE` 过滤右表字段，是否意外变成 `INNER JOIN`。
- 小表、大表、驱动表和数据倾斜是否符合实际数据量，而不是凭表名判断。
- 规范中的 Hive Join 文字为旧版本参考；当前 Hive/Spark 是否支持某种 Join 写法，应按实际引擎版本和现网语法验证，不把旧文档表述当成普遍技术事实。
- 严禁无证据添加看似相关的表、字段或血缘边。

### 7.3 去重与计数

- 业务事件是否存在重复上报、快照重复、流水重复或多版本记录。
- `ROW_NUMBER()` 的排序是否稳定、可复现，是否有并列值导致随机取数。
- 大数据量全局 `COUNT(DISTINCT)`，优先评估“先按业务键去重，再 `COUNT`”的执行方式；必须用验证 SQL 比较口径和性能。
- `UNION ALL` 是否重复接入同一业务范围；各分支是否互斥。
- 先 `SUM` 后去重、先去重后 `SUM` 的差异是否符合指标定义。

### 7.4 分区、时间与幂等

- 查询分区表是否在尽可能早的子查询中限制分区，避免全表扫描。
- 分区字段是否是业务认可的日期、时间或区域字段；不能因为方便直接用当前日期替代业务日期。
- `INSERT OVERWRITE`、`INSERT INTO`、动态分区和目标表形态是否匹配。
- 重跑同一周期是否结果稳定且不会重复追加；补数是否只影响指定分区。
- 状态快照、统计结果、流水、拉链的历史保存策略是否与表形态一致。
- 动态分区是否配置严格模式、分区数量和文件数量控制；未经任务实际需要，不得擅自打开非严格动态分区。
- 业务时间、ETL 时间、时区、日期边界和周/月起止口径是否明确。

### 7.5 性能与资源

按团队开发规范重点检查：

- 列裁剪：只选择下游实际需要的字段；禁止无依据保留 `SELECT *`。
- 分区裁剪：分区过滤尽量下推到读取表的最内层。
- 过滤下推：尽早过滤，减少每个阶段的数据量和中间结果依赖。
- Join 顺序：依据真实数据量选择驱动表；不能仅凭“小表”名称判断。
- `MAPJOIN`：只在确认小表记录数、大小、内存和平台参数后使用。原规范在不同章节给出过不同参考阈值（约 2000 行/25M 与 1000 行），不得硬编码为统一上线门槛，应以当前平台规范和实测为准。
- Shuffle：检查 Join、Group By、Distinct、Order By 是否制造不必要的全局 Shuffle。
- 数据倾斜：重点关注空值/默认值 key、低基数字段、热点用户或热点业务；必要时先采样分布，再设计拆分或加盐方案。
- 小文件：检查分区数量、Reducer 输出、动态分区和频繁临时表造成的小文件问题。
- 存储：大表压缩、列存/行存、分区与分布设计必须结合实际平台，不将 MPP 规则机械套到 Hive。
- 执行计划：对疑似慢 SQL 使用 `EXPLAIN` 或平台等价能力验证，不凭 SQL 外观直接判定性能。
- 每日定期作业原则上避免反复创建、删除大量临时表；如确需中间结果，应说明生命周期、清理策略和替代方案。

### 7.6 Union、排序与聚合专项

- `UNION ALL` 分支超过 2 个或单分支数据量较大时，按规范评估是否拆为多个写入步骤；必须结合业务互斥性和执行计划，不能机械改写。
- 多个数据集只是为补 0 后再汇总时，评估是否能用 Join 或预聚合减少中间结果膨胀。
- 全局 `ORDER BY` 可能集中到单个 Reduce；若业务只需局部有序或 Top N，评估 `SORT BY`、`DISTRIBUTE BY` 或先 `LIMIT`。
- `GROUP BY`、`DISTINCT`、全局 `COUNT(DISTINCT)` 必须检查 Reduce 压力和数据倾斜。

## 8. 问题分级

- **P0：必须修复才能上线**。例如：已由 SQL 或证据证明的多对多膨胀、重复写入造成结果错误、笛卡尔积导致目标结果失真、目标表粒度与指标口径确定性冲突、非幂等重跑会污染历史。
- **P1：高风险，需确认或修复后放行**。例如：输入表唯一性未证明、关键 Join 粒度不明、分区未裁剪、跨层引用不符合规范但可能有审批、时间口径未确认、字段类型不一致、指标对账缺失。
- **P2：建议优化**。例如：字段未做列裁剪、命名或注释不规范、可读性问题、可优化但未证明影响的 Shuffle、小文件或临时表风险。

P0 只能基于可证明的事实。无法从当前材料证明时，降为 P1，并写出验证方式。

## 10. 评审结论门槛

只有同时满足以下条件才能输出“通过”：

1. 三行粒度全部明确，并有证据或已验证的唯一性；
2. 无 P0、无 P1；
3. 目标表形态、分区和写入方式一致；
4. 跨层引用符合团队规范，或有明确审批依据；
5. 指标口径、时间口径、去重口径和空值处理已确认；
6. 关键分区已裁剪，性能风险有执行计划、样本或历史运行数据支持；
7. 测试和上线所需的 ETL Mapping、指标口径、测试报告、代码归档及运维信息已具备，或任务明确不适用。

缺少真实元数据时，结论最多为“有条件通过（待补元数据）”。

## 11. 实时链路补充

仅在用户明确目标为实时链路时启用：

- Kafka Topic、消费组、位点回溯和延迟；
- Flink watermark、迟到数据、状态和 checkpoint；
- 实时与离线修正是否重复写入；
- 实时与离线在时间字段、去重键、窗口、维表版本和修正机制上的口径一致性；
- Doris / MPP 表模型、分桶、排序键、分区和分布键。

若实时链路是否上线、是否允许离线修正覆盖未明确，不输出一致性通过结论。

## 12. 与 SQL 格式化的边界

本技能可以引用格式问题作为 P2，但不替代 SQL 格式化技能：

- 不为“美化”而修改 SQL 逻辑；
- 不擅自展开 `SELECT *`，除非评审目标明确要求列裁剪整改；
- 不擅自改写 Join、Union、聚合或表名；
- 不把格式正确当成业务正确；
- 不以“SQL 能运行”替代粒度、口径、幂等和数据质量验证。
