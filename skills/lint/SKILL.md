# Lint：知识库健康巡检

## 目标

对当前 Obsidian LLM Wiki 进行类似静态分析的巡检，准确识别结构、链接、索引、来源和知识冲突问题，并给出可执行的修复建议。

默认阶段严格只读：

- 不修改、删除、移动或重命名任何文件。
- 不自动补建页面或索引条目。
- 不扫描 `raw/` 正文，更不读取归档内容。
- 完成报告后，只有用户明确同意修复，才进入写入阶段。

## 当前仓库契约

检查范围：

- `wiki/sources/`：来源摘要
- `wiki/entities/`：人物、组织、模型、工具和产品
- `wiki/concepts/`：理论、技术、框架和方法论
- `wiki/syntheses/`：跨来源综合分析
- `wiki/index.md`：全局索引
- `wiki/log.md`：追加式操作日志
- `assets/`：Obsidian 嵌入附件的目标目录

来源只做路径存在性验证，不读取内容：

- `raw/`：待处理资料
- `raw/99-archive/`：规范归档目录
- `raw/999-archive/`：兼容旧归档目录（如存在）

`index.md` 和 `log.md` 是基础设施文件，不按普通知识页面要求 Frontmatter、被引用状态或 `## 关联连接`。

## 触发方式

- `/lint`
- `/scan`
- `/health`
- “检查知识库状态/健康度”
- “检查死链、孤岛、索引、Frontmatter、来源或知识冲突”

如果用户只要求检查某一类问题，可缩小报告范围；除非明确指定，否则执行完整巡检。

## 巡检流程

### 1. 建立页面清单

递归扫描 `wiki/` 下所有 `.md` 文件，并记录：

- 相对于 `wiki/` 的路径
- 文件基名（不含 `.md`）
- 所属分类目录
- Frontmatter 的 `title` 与 `type`
- 页面中的 `[[wikilink]]`、`![[embed]]` 和 `sources`

知识页面集合排除基础设施文件 `wiki/index.md`、`wiki/log.md` 与 `wiki/conventions.md`；`wiki/templates/` 为页面模板，同样不纳入知识页面集合。

如果四个知识目录都为空，且 `index.md` 也为空，将其识别为“尚未初始化内容的空知识库”，不要误报孤岛、索引缺失或健康率为零；报告为初始化状态。

### 2. 检查索引一致性

先完整读取 `wiki/index.md`，识别 `Sources`、`Entities`、`Concepts`、`Syntheses` 四个分类。本仓库 index.md 实际使用中文标题（`概念索引` / `实体索引` / `资料来源索引` / `综合分析索引`），中英文标题均应识别为对应分类。
检查：

- 文件存在但未登记：未同步索引。
- 索引已登记但文件不存在：失效索引条目。
- 同一页面被重复登记。
- 页面登记在错误分类下。
- 同名基名在多个目录出现，导致 `[[PageName]]` 解析歧义。
- 索引缺少必要分类标题，或内容存在但索引为空。

索引链接可写为 `[[PageName]]` 或 `[[PageName|显示文本]]`。解析时使用 `|` 左侧目标。

### 3. 检查 Obsidian 链接

解析以下形式：

- `[[PageName]]`
- `[[PageName|别名]]`
- `[[PageName#标题]]`
- `[[PageName#标题|别名]]`
- `[[#当前页标题]]`
- `![[附件.png]]`

判定规则：

- 忽略别名部分和 `#标题` 部分后检查页面目标。
- `[[#标题]]` 是当前页锚点，不按缺失页面处理。
- 不带路径的页面链接按文件基名匹配。
- 带路径链接统一 `/` 与 `\` 后匹配相对路径。
- Wiki 页面目标不存在时标记为死链。
- 嵌入附件在 `assets/` 或链接指定位置不存在时标记为缺失附件，不与页面死链混为一类。
- 外部 Markdown 链接 `[text](https://...)` 不作为 Obsidian 死链检查对象。

### 4. 检查孤岛与关联质量

统计知识页面之间的有效入链和出链，排除：

- 页面自引用
- `index.md` 的注册链接
- `log.md` 的操作记录链接

检查：

- 没有任何其他知识页面入链的页面：候选孤岛。
- 缺少 `## 关联连接` 的页面：结构缺失。
- `## 关联连接` 存在但没有有效知识页链接：空关联区。
Source 页面天然可能只被 Entity 或 Concept 引用。只要存在至少一个有效知识关系，就不判为孤岛。

### 5. 检查 Frontmatter 与分类

每个知识页面应包含合法 YAML Frontmatter：

```yaml
---
title: "页面标题"
type: concept | entity | source | synthesis
tags: [标签]
sources: ["raw/相对路径/文件.pdf"]
last_updated: YYYY-MM-DD
---
```

仓库现存两套 frontmatter 契约，检查时均视为合法：

- 新契约（AGENTS.md / 本文件）：`title` / `type` / `tags` / `sources` / `last_updated`
- 旧契约（wiki/conventions.md 与历史种子页）：`type` / `aliases` / `tags` / `status` / `created` / `updated` / `source`（或 `source_path`）

两套混用属于“契约不统一”，作为黄灯建议项报告，不自动改写，由用户决定统一方向。

检查：

- Frontmatter 缺失或 YAML 无法解析。
- 所属契约的必需字段缺失（新契约：`title`/`type`/`tags`/`sources`/`last_updated`；旧契约：`type`/`tags`/`created`/`updated` 及 `source` 或 `source_path`）。
- `type` 与目录不一致。
- `last_updated` 不是 `YYYY-MM-DD`。
- 新契约 `sources` 不是列表；旧契约 `source` 不是 `[[来源页]]` 引用；或非 Synthesis 页面没有可追溯来源。
- 同一页面的 `sources` 出现重复项。

命名不一致作为建议项，不自动判定为红灯：

- Entity 使用可读专名或 TitleCase（如 OpenAI、招商城科）。
- 其余页面使用中文描述性命名、无空格与特殊符号（conventions.md 约定），避免编号前缀。
- 同类型页面命名风格不一时，作为建议项提示。

### 5.5 检查动态源元数据

- `update_policy: live` 的 Source 页：`sources` 必须指向 `raw/98-活源/`，且必须含 `source_version`、`source_checked`；缺失或位置不符为黄灯。
- `update_policy: static` 的 Source 页：不应指向 `raw/98-活源/`（黄灯）。
- 提示项（非红灯）：若 live 源 `source_checked` 之后远端 git 有更新，提示"源已更新，建议 /sync"（需 `git fetch` 后对比，只读操作）。
- `## 版本变更` 区块存在时，确认新旧版本与 `source_version` 可对应。

### 6. 检查来源路径

只验证来源路径是否存在，不读取源文件。按页面采用的 frontmatter 契约处理：

0. 旧契约页面：`source` 为 `[[来源页]]` 引用时解析为来源页链接，仅验证对应来源页存在；`source_path` 存在时按 raw 相对路径验证。
1. 新契约：检查 Frontmatter `sources` 记录的原始 `raw/...` 路径。
2. 如果原路径因 ingest 已归档，再按相同相对结构检查 `raw/99-archive/...`。
3. 为兼容旧资料，也允许在 `raw/999-archive/...`（如存在）中确认存在。

仅当三个位置均不存在时报告“来源缺失”。不要因为资料已归档就误报。

### 7. 检查知识冲突

搜索包含 `## 知识冲突` 的页面，提取：

- 页面名称
- 冲突双方的简要说法
- 是否标注来源
- 是否存在“已解决”或明确结论

未解决冲突是认知技术债，报告但不自动选择任何一方。

### 8. 检查日志约束

对 `wiki/log.md` 做轻量结构检查：

- 日志条目是否使用 `## [YYYY-MM-DD] <动作> | <简述>`。
- 动作是否为 `ingest`、`query`、`lint`、`sync` 等约定类型。
- 是否出现明显重复的同次操作记录。

无法仅凭当前文件证明历史曾被覆盖，因此不要声称已验证“append-only 历史完整性”。

## 严重级别

- **红灯**：死链、缺失附件、索引指向不存在页面、无效 YAML、来源完全缺失、未解决知识冲突。
- **黄灯**：孤岛、未登记页面、错误分类、缺失字段、空关联区、命名不一致、重复索引。
- **绿灯**：通过检查的项目及数量。
- **信息项**：空知识库、当前页面总数、按类型分布等非故障状态。

## 报告格式

使用简体中文输出，不使用表情符号：

```markdown
# 知识库健康检查 - YYYY-MM-DD

## 概览
- 页面：N
- Sources / Entities / Concepts / Syntheses：N / N / N / N
- 红灯：N
- 黄灯：N

## 红灯问题
- [问题类型] `来源文件` -> `目标或原因`

## 黄灯问题
- [问题类型] `页面` - 建议动作

## 通过项
- [已通过的检查及数量]

## 修复顺序
1. [优先处理的具体问题]
```

没有问题时明确写“未发现结构性问题”，并说明仍存在的边界，例如未验证原始资料正文正确性。

## 修复阶段

只有用户明确要求修复后才执行：

1. 先列出拟修改文件和修复方式。
2. 优先修复确定性问题，例如去重索引、补登记、修正明确路径。
3. 死链存在多个候选目标时询问用户，不猜测。
4. 孤岛页面需要语义判断时，不创建虚假链接。
5. 知识冲突不得自动裁决。
6. 修复后重新运行完整巡检。
7. 在 `wiki/log.md` 追加：

```markdown
## [YYYY-MM-DD] lint | 修复知识库健康问题
- **结果**: 修复 N 项；剩余 N 项
- **变更**: [涉及页面或索引]
```

单纯生成只读报告时不写日志，避免检查行为本身污染知识库。

## 完成标准

- 报告基于当前文件实际扫描结果，不凭假设。
- Obsidian 别名和标题锚点未被误报。
- `index.md`、`log.md` 未被当作普通知识页。
- 已归档来源未被误报为缺失。
- 报告阶段没有修改任何文件。
- 所有问题都包含具体页面、原因和建议动作。
