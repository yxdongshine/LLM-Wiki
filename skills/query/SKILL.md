# Query：本地知识检索与综合

## 目标

将用户的问题转化为对当前 `wiki/` 的可追溯检索：

1. 先通过 `wiki/index.md` 理解知识库结构。
2. 深读最相关的知识页面，而不是只看文件名或摘要。
3. 区分本地事实、综合推断、知识冲突和通用知识。
4. 使用 Obsidian 双链标明本地依据。
5. 在用户同意时，将高价值综合结论保存到 `wiki/syntheses/`。

## 当前知识库范围

- `wiki/sources/`：从原始资料（公司开发规范、项目资料、学习笔记等）提炼的来源摘要
- `wiki/entities/`：人物、组织、模型、工具和产品
- `wiki/concepts/`：理论、技术、框架和方法论
- `wiki/syntheses/`：跨页面形成的综合分析
- `wiki/index.md`：检索第一入口
- `wiki/log.md`：追加式操作日志

Query 默认只检索 `wiki/`，不直接读取 `raw/99-archive/`（如存在旧归档目录 `raw/999-archive/` 同样排除）。用户明确要求核对原始资料时，应说明将进入来源核验，并遵循归档目录不可读取的项目约束。

## 触发方式

- `/query <问题>`
- “我的知识库/笔记/历史记录里关于 X 怎么说？”
- “之前整理过 X 吗？”
- “从这些资料/笔记中总结 X。”
- “查询 Wiki 中与 X 相关的概念、工具或资料。”

纯通用知识问题且没有任何“本地知识库”语境时，不应仅因出现“知识”或“记录”等宽泛词而误触发。

## 检索流程

### 1. 解析问题

识别：

- 核心主题及同义词、中英文名、缩写。
- 用户需要的任务类型：查事实、找页面、总结、比较、追溯来源或回顾历史结论。
- 时间、范围、项目/主题、实体或概念等限制条件。

不要在尚未检索前假定知识库中存在答案。

### 2. 必须先读全局索引

每次查询的第一步都是完整读取 `wiki/index.md`，从以下分类定位候选页面：

- Sources
- Entities
- Concepts
- Syntheses

匹配页面名、索引描述、别名、英文缩写和用户使用的近义表达。优先选择语义最直接的少量页面，避免无差别读取整个知识库。

### 3. 索引为空或疑似失同步时降级

当前项目可能处于尚未完成首次 ingest 的空库状态。如果 `wiki/index.md` 为空：

1. 检查 `wiki/sources/`、`entities/`、`concepts/`、`syntheses/` 是否也为空。
2. 四类目录均为空时，直接判定本地知识库尚无可查询内容。
3. 如果目录中存在页面但索引为空或没有相关条目，受控扫描 `wiki/` 的文件名、Frontmatter、标题和正文关键词。
4. 明确告知用户“索引未同步，本次使用目录降级检索”，并建议运行 `/lint`。

必须先读索引，但不能因为索引失同步而忽略实际存在的知识页面。

### 4. 分层扩展检索

按以下顺序逐步扩展，找到足够依据后停止：

1. 精确匹配页面名、`title`、索引描述。
2. 匹配标题、标签和 `## 关联连接`。
3. 搜索正文关键词、同义词、缩写和中英文变体。
4. 沿候选页面的有效 `[[wikilink]]` 扩展一层。

不要把 `wiki/log.md` 当作知识事实来源。只有当问题询问“什么时候摄取、查询或修复过什么”时，才读取日志。

### 5. 深读候选页面

完整读取最相关页面，重点提取：

- 页面定义和关键结论
- Frontmatter 中的 `type`、`sources`、`last_updated`
- 与问题相关的机制、步骤、条件、优缺点和案例
- `## 关联连接` 中需要补读的页面
- `## 知识冲突` 中尚未解决的不同说法

证据优先级：

1. Synthesis：适合回答已有综合结论，但仍需检查其引用页面。
2. Concept / Entity：适合定义、机制和对象说明。
3. Source：适合追溯某份原始资料（开发规范、项目资料、学习笔记等）的具体观点。
4. Log：仅适合回答操作历史。

页面没有来源或存在结构问题时，可以使用其内容，但需降低确定性并明确提示。

### 6. 综合回答

使用简体中文，先直接回答，再补充必要依据。

本地引用规则：

- 使用页面基名，不带目录和 `.md`：`[[page-name]]`。
- 一组连续观点来自同一页面时，在该段自然引用一次即可。
- 多页面共同支持结论时，可写为 `[[page-a]]、[[page-b]]`。
- 不要在同一句前后机械重复同一双链。
- 原文短句确有必要时使用 Markdown 块引用，并注明对应页面。

明确区分：

- **本地知识**：页面明确记载的内容，必须带双链。
- **综合推断**：由多个页面推导，写明“综合来看”或“可以推断”，并列出依据页面。
- **知识冲突**：并列呈现不同说法及来源，不替用户静默裁决。
- **信息缺口**：直接说明缺少哪类页面或来源。

推荐回答结构：

```markdown
[直接答案，包含 [[本地页面]] 引用]

## 依据
- [[页面名称]] - 与问题相关的关键内容

## 限制
- [冲突、来源缺失、索引失同步或信息不足]
```

简单问题不必强行使用完整结构。

## 本地无结果时的降级

只有完成索引读取和必要的降级检索后，才能判定“未找到”。

必须使用明确声明：

> 本地知识库中未找到，以下为通用知识回答。

随后可以给出通用回答，但不得使用 `[[wikilink]]` 伪装成本地来源。若问题涉及最新信息、医疗、法律、金融等需要外部核验的内容，应按当前工具与安全规则检索权威来源，不能只依赖模型记忆。

如果用户只要求查询本地知识库，不要擅自补充通用答案；改为说明未找到，并给出可摄取的资料方向。

## 保存高价值 Synthesis

当回答需要跨两个以上页面进行比较、归纳或形成可复用结论时，在回答完成后询问用户是否保存。未经用户同意，不写入 `wiki/syntheses/`。

建议文件名使用描述性 kebab-case，例如：

`agent-framework-comparison.md`

页面格式：

```markdown
---
title: "综合页面标题"
type: synthesis
tags: [主题标签]
sources: ["raw/相关原始路径"]
last_updated: YYYY-MM-DD
---

# 综合页面标题

## 结论

[综合结论]

## 分析
[比较、推导及适用边界]

## 关联连接
- [[source-page]] - 来源摘要
- [[concept-page]] - 相关概念
```

保存时：

1. 合并引用页面 Frontmatter 中真实存在的 `sources`，去重后写入。
2. 在正文中保留相关双链。
3. 将页面登记到 `wiki/index.md` 的 Syntheses 分类。
4. 避免与已有 Synthesis 重复；优先增量更新语义相同的页面。

## 查询日志

完成本地 Wiki 查询后，在 `wiki/log.md` 末尾追加：

```markdown
## [YYYY-MM-DD] query | 查询 <主题>
- **依据**: [[PageA]], [[PageB]]
- **输出**: 即时回答未保存
```

如果保存了 Synthesis：

```markdown
## [YYYY-MM-DD] query | 综合 <主题>
- **依据**: [[PageA]], [[PageB]]
- **输出**: 已保存至 [[synthesis-page]]
```

如果本地为空或无结果：

```markdown
## [YYYY-MM-DD] query | 查询 <主题>
- **依据**: 本地未找到相关页面
- **输出**: 通用回答未保存
```

日志只能追加，不得改写已有记录。若用户明确要求只读查询且不产生任何文件改动，则尊重该要求并跳过日志，同时在回答中简短说明。

## 禁止事项

- 禁止未检索就声称"知识库中记载"。
- 禁止将模型常识、外部网页内容或推断包装成本地页面内容。
- 禁止只读 `index.md` 的一句描述就回答复杂问题。
- 禁止为了满足回答而创建不存在的双链或虚构页面。
- 禁止在存在 `## 知识冲突` 时只呈现其中一方。
- 禁止自动保存 Synthesis。
- 禁止依赖当前仓库中不存在的 `CLAUDE.md`。
- **禁止编造字段名/表名/口径**。涉及数仓表结构、字段、SQL 关联键时，每个字段必须能指到 L1 证据（DDL 注释、现网脚本原文、数据字典、主人口述）；指不到的按 `AGENTS.md`「事实依据规则」列为待确认，不得靠"这类表通常有 X 字段"补全。
- **禁止跨表字段串味**。形近表（如 0154/0161 customer_account）字段各自查证，不互相套用。
- **别名不等于字段**。`x AS y` 只说明输出别名，不代表源表存在 `y` 字段。

## 完成标准

- 已首先读取 `wiki/index.md`。
- 已完整阅读足以支持回答的候选页面。
- 本地事实均有准确的 `[[wikilink]]`。
- 推断、冲突、信息缺口和通用知识已清晰区分。
- 索引为空或失同步时采用了正确降级策略。
- 查询日志已按约定追加，或因用户要求只读而明确跳过。
- 未凭模型记忆冒充本地知识。
